YumiVibe — Speaker Notes

5 minutes total. Read naturally, not word-for-word. These are talking points.

Slide 1 — Title5 sec

"Hi everyone, I'm Yuliya, and this is YumiVibe."

Slide 2 — The Problem20 sec

"So here's the thing — whatever you're doing, whether it's a workout, studying, or just chilling — you end up with five or more tabs open. Timer here, playlist there, to-do list somewhere else.

And if you want to skip a song while working out, you have to stop, find the right tab, click something. It breaks your flow every time.

There's no single app that combines productivity, entertainment, and mood in one place. Notion doesn't play music. Spotify doesn't have timers. YouTube doesn't have to-do lists. You're constantly switching contexts."

Slide 3 — The Solution15 sec

"YumiVibe puts everything in one place. Productivity blocks like timers and to-dos. Entertainment — YouTube and Spotify. Weather with AI outfit suggestions. And the star feature — voice control.

Say 'pause' and everything stops. Say 'next song' and it skips. No hands needed.

It's fully customizable — drag blocks, resize them, pick from six color themes. Each user has their own dashboards that persist in the cloud. It works like a real product, not a demo."

Slide 4 — The First Prompt15 sec

"We started with a detailed CLAUDE.md — our single source of truth. It defined the tech stack, all eleven block types, strict coding rules — no 'any' types, files under 300 lines, Zod validation on every route.

Every decision we made traced back to this file."

Slide 5 — Build Montage20 sec

"The build had four phases and 52 commits total.

Phase one — frontend. One massive initial prompt gave us all eleven blocks, the drag-and-drop grid, themes, voice control. It worked on the first try.

Phase two — backend. About eight commits. PostgreSQL setup, real API wiring, email/password auth. This needed iteration — plan mode, implement, fix, verify.

Phase three — Spotify. This was the hardest. Twenty commits. We started with a simple embed, then added OAuth, then the Web Playback SDK, then had to build a unified player for both playlists and user's own music. Not everything worked first try — the embed and SDK kept conflicting. We iterated until it was right.

Phase four — audit and polish. Twenty-three commits. Security audit found real issues — we fixed them all. Color theming took three attempts to get right. Every fix verified with build plus tests.

We used parallel agents throughout — up to three running simultaneously. Some prompts worked perfectly, some needed multiple iterations. That's the honest journey."

Slide 6 — Features10 sec

"Quick overview — eleven block types. Clock, pomodoro, timer, weather with real data and AI clothing tips, todos, notes, quotes, YouTube with playlists, Spotify with full SDK control, greeting, and title. All draggable and resizable."

Slide 7 — Voice Control10 sec

"Voice control is the star feature. Click the mic, speak naturally. 'Play', 'pause', 'next song', 'mute'. No wake word needed. Perfect for workouts — you never touch the screen."

Slide 9 — Testing & Security15 sec

"This isn't just a demo — it's tested like a real product. 244 tests across 16 files. Every service, every hook, every validator, every API route.

We ran a full security audit — OWASP Top 10 checks. Found issues with token storage, missing CSRF protection, brute force vulnerability on login. Fixed every single one. Rate limiting per user and per IP, security headers, parameterized SQL everywhere. Zero injection risk."

Slide 10 — Tech Stack10 sec

"Quick stack overview — Next.js 14 with React 18, chosen for stability and ecosystem compatibility. TypeScript in strict mode. PostgreSQL on Neon. Spotify Web Playback SDK for real music control. Claude Haiku via AWS Bedrock for AI clothing suggestions. All deployed on Vercel."

Slide 11 — Lessons Learned20 sec

"Three things surprised us.

First — Spotify's embed is a black box. No skip, no next. We had to build a unified SDK player to get real voice control.

Second — security is layers. Hash fragments, CSRF state, rate limiting — each one catches what others miss.

And third — CLAUDE.md pays for itself. Every strict rule we wrote upfront caught real bugs during the audit."

If Judges Ask Questions

"Why Next.js 14 and not 15?"

"We chose the stable LTS release. All our dependencies — react-grid-layout, Spotify SDK — are fully compatible. Next.js 15 with React 19 still had ecosystem gaps with third-party packages."

"Why raw SQL instead of an ORM?"

"Full control over queries, no abstraction leaks. With parameterized queries and Zod validation, we get type safety without the overhead of Prisma or Drizzle."

"How does voice control work?"

"Chrome's Web Speech API. Continuous listening, pattern matching on transcripts. Commands route through a pub/sub media event system to YouTube and Spotify blocks."

"What about mobile?"

"The grid is responsive — three breakpoints. Blocks reflow on tablet and stack on mobile. Voice control is Chrome-only though."

"How do you handle Spotify for non-Premium users?"

"They get the embed player — paste a URL, play within the embed. Premium users who connect get the full SDK with skip, next, and voice control."

"How did you use Claude in the build?"

"Claude Code with parallel subagents. Up to three agents running simultaneously for research, code fixes, and testing. The CLAUDE.md file was our prompt foundation — every agent decision traced back to it."
